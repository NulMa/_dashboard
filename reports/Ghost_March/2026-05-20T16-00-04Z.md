# Ghost_March — UI 전환·데이터 패치 스냅샷

## 1. 주요 변경사항
- MainMenu 전용 씬이 추가되고 `UIGameFlow`가 메인 메뉴와 인게임 HUD 흐름을 분리했다. `UIManager`의 씬 유지 성격도 약해져 이전보다 테스트 격리가 쉬워졌다.
- Live Data Patch 서비스, DTO, 기본 JSON, 브리지가 추가되어 앱 시작 시 수치 패치를 로드하는 구조가 생겼다.
- 레벨업, 메인 메뉴, 아이템 선택, 무기 각성 smoke test가 추가되어 UI Toolkit 전환의 자동 검증 범위가 넓어졌다.
- HUD 무기 슬롯, 각성 아이콘, Resources sprite 캐싱, `IsEmpty` 사용 전환 등 UI·브리지 hot path의 반복 할당과 불필요한 카운트 계산이 줄었다.
- Burst 적용과 롤백이 여러 차례 있었고, 일부 시스템은 안정성 때문에 non-Burst로 남았다. 이 판단은 현실적이지만 성능 기준 재측정이 필요하다.

## 2. 코드 품질 리뷰
이번 변경은 방향이 좋다. UI가 직접 게임 규칙을 소유하던 흐름을 줄이고, ECS 이벤트와 브리지 계층으로 역할을 분리하려는 의도가 코드와 문서에 같이 반영되어 있다. 특히 `VerticalSliceDebugSnapshot`에 무기 상태를 추가하고 HUD가 이를 표시하게 한 변경은 “보여주기 위해 런타임을 직접 뒤지는 UI”가 아니라 “관측 스냅샷을 소비하는 UI”로 이동했다는 점에서 바람직하다.

다만 smoke runner들이 `BindingFlags.NonPublic`로 private 필드와 메서드를 호출한다. 왜 문제냐면 화면 내부 구현 이름이 바뀌면 실제 게임 기능은 정상이어도 테스트가 깨지고, 반대로 테스트 편의를 위해 private 구조가 고정되는 역의존이 생긴다. 개선하려면 editor/test 전용 assembly에서 접근 가능한 작은 테스트 hook 또는 public command method를 분리해, “사용자 행동을 제출한다”는 수준의 API만 노출하는 편이 낫다.

자료구조/복잡도/할당 관점에서는 분명한 전진이 있다. `Resources.LoadAll` 중복 제거, sprite 캐싱, `CalculateEntityCount()==0`을 `IsEmpty`로 바꾼 작업은 UI 표시와 브리지 경로의 불필요한 로드·카운트 비용을 줄인다. 반면 `LevelUpUiSmokeTestRunner.HasPendingItemSelectionEvents()`는 이벤트 버퍼 1개 확인을 위해 `ToEntityArray(Allocator.Temp)`를 만든다. 테스트 코드라 영향은 낮지만, 이미 프로젝트가 `GetSingletonEntity()`로 방향을 잡았으므로 같은 패턴으로 맞추는 편이 일관적이다.

## 3. 진행도 평가
네트워크 구현은 아직 실제 코드가 없으므로 이번 평가는 `framework/hybrid/custom-network` 중 어느 하나로 확정할 단계가 아니다. 현재는 싱글플레이 DOTS 수직 슬라이스 기준으로 본다. 그 기준에서는 메인 메뉴에서 게임 진입, HUD, 레벨업, 무기 각성, 데이터 패치, 성능 문서까지 이어져 제출 가능한 루프에 가까워졌다.

진행도는 72로 본다. 자동 smoke와 문서화가 강해졌고 반복 시연 가능성도 높아졌다. 그러나 Burst 적용 범위가 아직 흔들렸고, 모바일 실기기 성능 기준이 최종 판정되지 않았으며, 도감·일시정지 같은 UI 경로는 자동 검증이 덜 닫혔다. 위험도는 high까지는 아니지만 medium을 유지해야 한다.

## 4. 다음 권장사항
- 일시정지와 도감 화면 smoke를 추가해 UI Toolkit 전환의 빈 구멍을 닫아야 한다.
- UI Toolkit 전환, 브리지 비활성화, Burst 롤백 이후 전체 Play Mode smoke를 한 번의 기준 로그로 고정해야 한다.
- `digitMaterial`과 damage digit atlas 할당을 끝내고 GPU 렌더 브리지의 시각 누락 가능성을 제거해야 한다.
- `EnemySeparationSystem` 최적화 뒤 모바일 목표 프레임 기준으로 다시 측정해야 한다.
- smoke runner의 private reflection 의존을 테스트 전용 API로 줄여야 한다.

## 5. 문서화 상태
design 점수는 8이다. `docs/planning/game-design-spec.md`, `docs/planning/ui-plan.md`, 발표 요약 문서가 코어 루프와 UI 흐름을 충분히 설명한다. 다만 일부 unlock·업적 규칙은 아직 코드와 문서 사이의 단일 출처가 약하다.

technical 점수는 9다. assembly boundary, live data patch boundary, migration 문서, handoff 문서가 신규 유입자가 구조를 따라갈 수 있을 정도로 촘촘하다. 이번 diff에서도 변경 이유와 검증 결과가 잘 남았다.

spec 점수는 8이다. UI 화면 목록, DOTS 전환 항목, 성능 수치, live data patch schema가 테스트 체크리스트로 활용 가능한 수준이다. 남은 빈틈은 최종 모바일 기준 수치와 unlock/balance 단일 표다.

## 6. Backlog
- 도감·업적 unlock 규칙이 코드 상수와 문서 트레이드오프에 분산되어 있다. 왜 문제냐면 세이브, 밸런스 패치, UI 표시가 서로 다른 기준을 가질 수 있다. unlock 조건을 데이터 또는 서비스 경계로 옮기는 편이 좋다.
- `RunSessionConfig`가 임시 static 세션 상태로 남아 있다. 지금은 캐릭터 선택 전달용으로 충분하지만, 캐릭터 스탯·로비·재시작이 붙으면 씬 재로드와 테스트 격리 문제로 커진다.

## 7. 이전 Backlog 해결
- UI 화면 스택 결합 문제는 별도 MainMenu 씬, `UIGameFlow` 모드 분리, `UIManager`의 `DontDestroyOnLoad` 제거로 핵심 위험이 해소됐다.
- HUD 무기 슬롯 문제는 `VerticalSliceDebugSnapshot`에 무기 레벨·각성 상태가 추가되고 `HUDScreen`이 이를 표시하도록 바뀌어 해결됐다.
