# Ghost_March — UI 수직슬라이스 확장 스냅샷

## 1. 주요 변경사항
- 설정, 튜토리얼, 로딩, 결과 화면이 추가되고 MainMenu·Pause·HUD 흐름이 UI Toolkit 기준으로 더 완결됐다.
- damage digit는 표시 모드, per-enemy aggregation, active cap 80, 모바일 가독성 확대까지 들어가 성능·가독성 양쪽을 의식한 개선이다.
- 최종 `DotsVerticalSlice.unity`에는 SFX, `healSoulMaterial`, `digitMaterial`, 신규 화면 참조가 상당수 고정됐다. 직전 Inspector 미할당 이슈는 런타임 씬 기준으로 많이 해소됐다.
- Hard mode 설정과 UI 선택지가 추가됐고, 보스 경고 배너와 업적 toast가 들어가 플레이 피드백이 강화됐다.
- 반대로 `DotsVerticalSliceBakingHost.unity`가 거의 비워지고 실제 씬 YAML이 대폭 재작성되어, 검증 없이는 참조 회귀 위험이 크다.

## 2. 코드 품질 리뷰
이번 변경은 “UI 화면을 실제 플레이 루프에 붙인다”는 목표가 분명하고, 화면 단위 클래스와 UXML/USS를 계속 분리한 점은 좋다. 특히 Pause에 있던 digit 설정을 Settings로 이동하고, RunResult를 HUD 내부 임시 오버레이가 아니라 별도 화면으로 분리한 결정은 유지보수 관점에서 맞다. 다만 화면 수가 늘어난 만큼 `ScreenId`, UXML name, `UIDocument`, bridge 참조가 모두 런타임 직렬화에 의존한다. 이 계층은 컴파일 성공만으로 안전하다고 볼 수 없다.

자료구조/복잡도 관점에서는 damage digit 쪽에서 의미 있는 전진이 있다. per-enemy damage aggregation과 active digit cap은 다수 적 상황에서 엔티티·렌더 인스턴스 폭증을 막는 직접적인 방어선이다. 현재 diff 범위에서 `Update` hot path의 LINQ, 반복 `ToArray`, 명확한 O(n²) 조회 같은 새 문제는 확인되지 않는다. 다만 `MaxEnemies: 2500`으로 시연 목표가 올라갔으므로, `EnemySeparationSystem`과 digit/effect spawn 계열은 모바일 계측 없이 “최적화됐다”고 선언하면 안 된다.

Unity 관점의 가장 큰 위험은 씬 직렬화 변경 폭이다. `DotsVerticalSlice.unity`는 화면 오브젝트와 bridge fileID가 전면 재배치됐고, BakingHost는 부트스트랩과 UI 루트가 제거됐다. 의도된 구조 단순화라면 좋지만, 이 상태는 반드시 실제 PlayMode scene load, 화면 전환 smoke, 오디오 이벤트 smoke로 닫아야 한다. 아니면 다음 변경에서 “씬은 열리지만 특정 버튼만 무반응” 같은 비용 큰 결함으로 돌아온다.

## 3. 진행도 평가
네트워킹 코드는 현재 평가 대상에서 사실상 해당 없음이다. 따라서 진행도는 싱글플레이 DOTS 수직 슬라이스 기준으로 본다. 이번 범위는 UI/UX 완성도, 설정 저장, 난이도 선택, 결과 화면, 피드백 연출이 한꺼번에 들어가 제출 가능한 데모 형태에 가까워졌다.

다만 제출 안정성은 아직 70%대 초반으로 보는 것이 맞다. 이유는 기능이 부족해서가 아니라, 씬 재작성과 신규 화면 증가 대비 자동 검증 근거가 아직 약하기 때문이다. 핵심 루프가 반복 실행 가능하다는 PlayMode 증거가 붙으면 80%대로 올릴 수 있다.

## 4. 다음 권장사항
- `DotsVerticalSlice`와 `MainMenu`를 실제 PlayMode 로드로 검증하고, 부트스트랩·Bridge 참조 누락을 먼저 닫아라.
- Rebuild All Scenes 산출물이 동일 smoke를 통과하는지 고정해라. 씬 빌더와 수동 씬이 갈라지면 회귀 추적이 어려워진다.
- UI smoke 범위를 Settings, Tutorial, Loading, RunResult까지 넓혀라. 지금은 화면 수 증가가 리스크 증가로도 작동한다.
- Hard mode가 UI 선택에서 ECS spawn interval과 HP scale까지 이어지는지 계측해라.
- damage digit/effect 크기와 separation 성능은 모바일 기기 기준 프레임으로 다시 판정해라.

## 5. 문서화 상태
design은 8점이다. `docs/planning/game-design-spec.md`, `ui-plan.md`, `singleplayer-ui-completion-plan.md`가 화면 흐름과 플레이 의도를 충분히 담고 있다. 다만 일부 신규 정책은 코드 상수와 계획 문서에 나뉘어 있어 밸런스 문서로 바로 쓰기에는 흔들림이 있다.

technical은 8점이다. assembly boundary, UI Toolkit runtime structure, rebuild strategy, live data patch boundary 같은 문서가 있어 신규 유입자가 구조를 따라갈 수 있다. DOTS 전환 과정의 시행착오도 troubleshooting과 migration 문서에 남아 있어 실무 가치가 높다.

spec은 7점이다. 기능 목록과 씬/화면 흐름은 비교적 구체적이지만, unlock 조건, hard mode 배율, 모바일 성능 합격선이 테스트 체크리스트 형태로 완전히 고정되지는 않았다. 다음 단계는 “설명 문서”가 아니라 “판정표”로 정리해야 한다.
