# Ghost_March — DOTS UI 통합 스냅샷

## 1. 주요 변경사항
- DOTS 수직 슬라이스에 UI Toolkit 기반 HUD, 레벨업, 무기 정보, 캐릭터 선택, 업적, 도감, 일시정지 화면이 대거 추가됐다.
- 적 타입 체계가 normal, swarm, elite, boss 방향으로 확장됐고 테스트용 mob spawn 구성도 별도 assembly로 분리됐다.
- EnemySeparationSystem은 double-buffer 및 셀 크기 조정으로 병목을 줄이려는 시도가 들어갔다. 실패한 반경 축소를 되돌린 점도 판단이 좋다.
- 피격 vignette, 모바일 UI 아이콘, 입력 command gauge 등 플레이 피드백이 보강됐다.
- `ui-plan.md`, perf roadmap, handoff 문서가 갱신되어 작업 맥락 추적성이 좋아졌다.

## 2. 코드 품질 리뷰
전반적으로 이번 변경은 “기능을 화면에 얹는 단계”로서는 상당히 큰 전진이다. 특히 기존 uGUI bridge를 바로 지우지 않고 DOTS/UI Toolkit 쪽으로 병렬 이식한 선택은 검증 가능한 전환이라는 점에서 좋다. 다만 `HUDScreen.cs`와 `LevelUpScreen.cs`는 화면 조회, 리소스 로딩, 상태 갱신, 입력 처리, ECS 이벤트 발행이 한 클래스 안에 몰려 있다. 지금은 수직 슬라이스라 허용 가능하지만, 다음 화면이 붙으면 디버깅 비용이 급격히 오른다. 화면별 View binding, state adapter, command handler를 작게 나누는 쪽이 낫다.

명확한 버그 신호가 있다. `LevelUpScreen.BuildCandidates()`는 성장 후보가 0개일 때 길이 3짜리 `int[]`를 만들고 일부만 Heal로 채운다. 나머지 기본값 0은 `VerticalSliceItemType.Melee`로 해석될 수 있어, 만렙 또는 후보 없음 상태에서 잘못된 선택지가 노출될 위험이 있다. 왜 문제인가 하면 성장 제한 규칙이 UI에서 우회되기 때문이다. 개선은 후보가 없으면 Heal 단일 후보만 반환하거나, 카드 수를 실제 후보 수에 맞추는 방식이 적절하다.

자료구조/복잡도 측면에서는 핫패스에 치명적인 LINQ나 반복 `ToArray` 남용은 보이지 않는다. `NativeList` 후보 구성은 레벨업 이벤트 시점이라 비용이 작다. 대신 UI `LateUpdate()`에서 여러 스타일을 매 프레임 갱신하는 구조는 화면 수가 늘면 비용이 누적된다. 값이 바뀐 경우에만 style write를 수행하는 현재 캐시 패턴을 command arrow, floating bar까지 더 일관되게 확장해야 한다.

## 3. 진행도 평가
네트워킹 코드는 아직 본격 구현 대상이 아니므로 진행도는 framework/hybrid/custom-network가 아닌 단일 플레이 DOTS 수직 슬라이스 기준으로 본다. 반복 플레이 루프, 적 스폰, 피격, 레벨업, 결과 표시, 주요 UI가 붙어 제출 가능한 형태에 가까워졌다.

다만 메인 메뉴 흐름, 캐릭터 선택 타이밍, 결과 화면의 메인 메뉴 복귀가 문서상 트레이드오프로 남아 있다. 따라서 “시연 가능한 수직 슬라이스”는 60% 후반으로 평가하지만, 제품 흐름 완성도는 아직 고정되지 않았다. risk는 high까지는 아니나, UI 스코프가 빠르게 커지고 있어 medium이 맞다.

## 4. 다음 권장사항
- `LevelUpScreen.BuildCandidates()`의 후보 없음 처리를 먼저 고친다. 이는 밸런스 문제가 아니라 규칙 위반 버그다.
- UI Toolkit 화면마다 `Root.Q()` 결과 검증을 추가하고, UXML name 변경 시 즉시 실패하게 만든다.
- 메인 메뉴를 별도 씬으로 둘지 단일 씬 overlay로 둘지 결정한다. 이 결정 없이는 재시작과 캐릭터 선택이 계속 흔들린다.
- smoke test를 단순 생존 루프에서 UI 조작 루프로 확장한다. 레벨업 카드 선택, Pause, WeaponInfo, Bestiary 진입까지 자동 확인해야 한다.
- EnemySeparationSystem 최적화는 문서상 완료 표시만 하지 말고 모바일 목표 기기 기준 수치를 다시 남긴다.

## 5. 문서화 상태
design은 8점이다. `docs/planning/game-design-spec.md`와 `docs/planning/ui-plan.md`가 화면 흐름, 캐릭터, 업적, UI 요구를 상당히 구체적으로 다룬다. 다만 일부 핵심 선택이 트레이드오프로 남아 있어 9점은 아니다.

technical은 9점이다. assembly boundary, folder layout, DOTS rebuild strategy, verification loop, render profile 분석이 잘 갖춰져 있다. 신규 인원이 구조를 파악하기에 충분하다.

spec은 8점이다. legacy runtime spec, weapon/equipment spec, scene-prefab baseline, UI plan이 테스트 체크리스트로 쓸 수 있는 수준이다. 단 unlock 매핑과 결과 화면/메뉴 전환의 확정 사양은 아직 부족하다.

## 6. Backlog
- UI 화면 스택이 `UIManager.Instance`와 씬 직렬 참조에 묶여 있다. 지금은 빠르지만 씬 재로드, 테스트 격리, 메뉴 씬 분리에서 비용이 커진다.
- HUD 무기 슬롯은 아직 스냅샷에 데이터가 없어 비활성 처리되어 있다. 플레이어 성장 피드백의 핵심이므로 장기 미구현으로 남기면 안 된다.
- 도감과 업적 unlock 규칙이 `BestiaryScreen`의 코드 상수와 `ui-plan.md`의 미확정 항목에 나뉘어 있다. 저장 데이터 contract를 먼저 확정해야 한다.
