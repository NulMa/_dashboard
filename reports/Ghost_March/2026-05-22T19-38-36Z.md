# Ghost_March — UI·연출 통합 스냅샷

## 1. 주요 변경사항
- UI Toolkit 화면들이 개별 UIDocument 기반으로 재배치되고 SafeAreaAdapter가 추가됐다. 모바일 노치·해상도 대응을 시작한 점은 방향이 좋다.
- DotsVerticalSlice와 BakingHost 씬이 크게 재작성됐다. 화면별 GameObject, PanelSettings, SubScene, Bridge 구성이 한 번에 바뀌어 검증 범위가 커졌다.
- 히트 비네트용 Global Volume과 URP 후처리 설정이 복원됐다. 특수 이동 연출과 컷신 경계 문서도 추가되어 연출 파이프라인 의도가 명확해졌다.
- Achievement, Bestiary, LevelUp, HUD 등 화면 코드와 UXML/USS가 함께 수정됐다. 단순 스타일 수정이 아니라 런타임 화면 전환 안정성까지 영향권이다.

## 2. 코드 품질 리뷰
이번 변경은 기능 추가보다 “씬·UI 조립 방식 재정렬”의 성격이 강하다. SafeAreaAdapter를 화면마다 붙인 선택은 모바일 대응을 중앙화하려는 좋은 방향이다. 다만 모든 화면 GameObject와 UIDocument를 씬 YAML에 직접 확장하면서, 참조 누락이 나면 컴파일이 아니라 런타임 화면 전환에서 터지는 구조가 됐다. 이런 변경은 반드시 자동 smoke가 같이 따라와야 한다.

가장 큰 위험은 DotsVerticalSlice와 BakingHost의 책임 경계가 흐려진 점이다. diff 상 BakingHost에는 VerticalSliceBootstrap, AudioBridge, GPURenderBridge, CommandInputBridge가 대량 배치되어 있고, DotsVerticalSlice 쪽은 UI Root와 Volume 중심으로 재구성된 흔적이 강하다. 실제 런타임 씬에서 Bootstrap과 Bridge가 기대한 위치에 남아 있는지 확인하지 않으면, 메인 메뉴에서 게임 진입 시 UI만 있고 ECS 부팅이 실패하는 문제가 생길 수 있다.

자료구조/복잡도 관점에서는 이번 diff 범위에서 명확한 O(n²), LINQ 할당, hot path 컬렉션 복사 문제는 확인되지 않는다. 현재 우선순위는 자료구조 최적화가 아니라 씬 참조 무결성이다. Unity 프로젝트에서는 YAML 참조가 조용히 깨지는 비용이 더 크므로, UIDocument sourceAsset, PanelSettings, Bridge 직렬화 필드를 검사하는 smoke가 현재 구조의 실질적인 안전장치다.

## 3. 진행도 평가
네트워킹 코드는 확인되지 않으므로 구현 경로는 싱글플레이 수직 슬라이스로 본다. UI, 후처리, 특수 이동 연출, 문서화가 함께 전진했고, 제출 가능한 데모의 외형 품질은 분명히 올라갔다. 그래서 진행도는 70%로 평가한다.

다만 risk_level은 high다. 이유는 기능 위험이 아니라 통합 위험이다. 씬 파일 두 개가 대규모로 재작성됐고, 이전 TODO였던 Rebuild All Scenes와 전체 PlayMode smoke 검증이 아직 증거로 닫히지 않았다. 지금 상태에서 한 번의 씬 로드 실패가 데모 전체를 멈출 수 있다.

## 4. 다음 권장사항
- DotsVerticalSlice를 직접 로드해 Bootstrap, SubScene, Bridge, UI Root가 모두 살아 있는지 PlayMode에서 검증한다.
- Rebuild All Scenes 실행 결과를 MainMenu → DotsVerticalSlice 실제 진입까지 포함해 고정 테스트로 남긴다.
- UI Toolkit smoke를 HUD, 레벨업뿐 아니라 Pause, Bestiary, Achievement, Evo까지 확장해 화면 겹침 회귀를 잡는다.
- BakingHost와 런타임 씬의 SFX fileID 0 상태를 확인해 의도된 무음과 누락을 분리한다.
- 모바일 해상도에서 damage digit, 특수 이동 타격 이펙트, Safe Area 적용 결과를 실기 또는 GameView 프리셋으로 캡처한다.

## 5. 문서화 상태
design은 8점이다. `docs/planning/game-design-spec.md`, `docs/planning/ui-plan.md`, 발표 요약 문서가 게임 루프와 화면 구성을 설명하고 있어 실무 기준으로 충분하다. 다만 unlock 조건과 일부 밸런스 값은 아직 구현 코드와 문서 사이에 나뉘어 있다.

technical은 9점이다. assembly boundary, UI Toolkit runtime structure, post-processing and cutscenes, rebuild strategy 문서가 신규 투입자가 구조를 따라갈 수 있을 정도로 구체적이다. 이번 커밋에서 후처리·컷신 문서가 추가된 점도 좋다.

spec은 8점이다. 화면 목록, 씬 구성, 마이그레이션 체크리스트, 리소스 맵이 있어 테스트 기준으로 쓸 수 있다. 남은 약점은 “자동 검증 결과”가 사양 문서와 연결되지 않아, 어떤 체크가 통과해야 제출 가능인지 마지막 판정표가 부족하다는 점이다.
