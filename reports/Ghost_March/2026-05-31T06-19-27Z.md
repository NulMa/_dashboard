# Ghost_March — 모바일 수직 슬라이스 검증 스냅샷

## 1. 주요 변경사항
- 모바일 실행 흐름이 크게 정리됐다. 메인 메뉴 복귀, 포기 처리, 결과 화면, 레벨업 선택, 씬 재시작 회피가 여러 커밋으로 보강됐다.
- UI Toolkit 쪽은 `SingleplayerUiFlowSmokeTestRunner`, `UIRegistrationSmokeTestRunner` 추가로 이전보다 자동 검증 범위가 넓어졌다.
- live data 파이프라인이 CSV→JSON 생성, 기본 리소스, S3 호환 배포 workflow까지 이어졌다. 데이터 운영 기반은 좋은 방향이다.
- 오디오 설정, BGM/SFX 자산, 모바일 화면 폴리시, 후처리 튜닝 씬이 들어오며 제출용 폴리싱 단계로 이동했다.
- 단, `PostProcessTuning.unity`가 11만 줄 이상으로 추가되어 리뷰 가능성과 충돌 관리 측면에서는 명확한 위험 신호다.

## 2. 코드 품질 리뷰
이번 범위의 긍정적인 점은 “플레이 가능한 흐름”을 우선 고정했다는 점이다. `fix(flow)`, `fix(levelup)`, `fix(ui)` 계열 커밋이 단발 수정이 아니라 smoke runner와 문서 기록으로 이어진 점은 좋다. 특히 UI Toolkit 전환 이후 가장 위험했던 화면 등록, 일시정지, 결과, 튜토리얼, 설정 흐름을 자동화 대상으로 올린 것은 이전 리포트 대비 실질적인 전진이다.

반대로 변경 폭이 너무 넓다. `VerticalSliceBootstrap.cs`, `VerticalSliceGPURenderBridge.cs`, `VerticalSliceAudioBridge.cs`가 각각 수백 줄 단위로 증가했고, 게임 흐름·렌더링·오디오·데이터 패치가 같은 기간에 동시에 움직였다. 이런 구조는 버그가 나면 원인을 좁히기 어렵다. 개선하려면 브리지별 책임을 “ECS 상태 읽기”, “Unity 표현 갱신”, “설정 적용” 단위로 더 분리하고, 각 브리지에 최소 smoke나 debug snapshot 검증을 붙이는 것이 맞다.

자료구조/복잡도 관점에서는 diff 본문이 충분히 노출되지 않아 특정 hot path의 `List.Find`나 LINQ 할당을 단정할 근거는 부족하다. 다만 `PostProcessTuning.unity`처럼 대량 타일 GameObject를 씬 YAML로 직접 보관하는 방식은 자료구조 선택의 문제에 가깝다. 현재 비용은 리뷰·merge·재생성 검증 비용 폭증이고, 개선 방향은 타일/프리뷰를 에디터 생성기와 작은 설정 asset으로 재생성하는 것이다. 이 프로젝트는 이미 scene builder를 쓰고 있으므로 생성 산출물 최소화가 특히 의미 있다.

## 3. 진행도 평가
네트워킹 코드는 없으므로 구현 경로는 싱글플레이 DOTS/Hybrid 수직 슬라이스로 본다. 제출 가능한 플레이 루프 관점에서는 메인 메뉴, 캐릭터 선택, 전투, 레벨업, 포기, 결과, 재시작까지 이어지는 흐름이 상당히 갖춰졌다. Android 빌드 러너와 APK 검증 기록도 있어 진행도는 76으로 평가한다.

다만 위험도는 낮지 않다. 대형 씬 YAML, 대량 브리지 수정, 모바일 시각 효과 튜닝, live data override가 한 번에 들어왔다. “Editor smoke 통과”와 “실기 반복 시연 안정성” 사이에는 아직 간격이 있다. 지금 단계에서 가장 중요한 것은 기능 추가가 아니라 재현 가능한 모바일 smoke를 고정하는 것이다.

## 4. 다음 권장사항
- `DotsVerticalSlice`와 `MainMenu`를 Android 빌드 기준으로 반복 실행하고, 씬 로드·메뉴 복귀·런 재시작을 smoke 기준에 묶어야 한다.
- `PostProcessTuning.unity`는 리뷰 가능한 설정 asset과 생성기 중심으로 축소해야 한다. 11만 줄 YAML은 장기 유지보수에 부적합하다.
- damage digit, 특수 이펙트, vignette, outline은 실제 모바일 해상도와 밝기에서 가독성 기준을 다시 잡아야 한다.
- Hard mode와 live data patch의 적용 순서를 테스트해야 한다. 밸런스 수치가 어느 경로에서 최종 승리하는지 명확해야 한다.
- `EnemySeparationSystem`과 Burst 제외 시스템은 Unity/Entities 현재 버전에서 성능·컴파일 기준을 다시 확인해야 한다.

## 5. 문서화 상태
design은 8점이다. `docs/planning/game-design-spec.md`, `ui-plan.md`, `singleplayer-ui-completion-plan.md`가 현재 게임 루프와 화면 구성을 설명하고 있어 실무적으로 쓸 수 있다. 다만 일부 unlock·밸런스 규칙이 코드와 분산되어 설계 결정의 단일 출처는 아직 약하다.

technical은 9점이다. assembly boundary, UI Toolkit runtime 구조, live data patch boundary, Android release build, rebuild strategy 문서가 풍부하다. 신규 작업자가 구조를 따라가기 충분한 수준이다.

spec은 8점이다. live data CSV, generated JSON, validation checklist, unlock-save contract checklist가 테스트 기준으로 활용 가능하다. 다만 모바일 실기 성능 기준과 이펙트 가독성 기준은 문서가 있어도 최신 코드 변경과 함께 재측정이 필요하다.

## 6. Backlog
- 도감·업적 unlock 규칙은 아직 해결되지 않았다. `BestiaryScreen.cs`에 `unlockKills`가 남아 있고, `ui-plan.md`에도 도감·업적 흐름이 별도로 남아 있어 밸런스 변경 검증 경로가 분산된다. ScriptableObject 또는 live data 계약으로 unlock 기준을 모으고, 화면 코드는 표시만 담당하게 바꾸는 것이 맞다.
