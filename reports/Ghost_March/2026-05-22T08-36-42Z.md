# Ghost_March — UI 재빌드 수직 슬라이스 스냅샷

## 1. 주요 변경사항
- MainMenu와 DotsVerticalSlice 씬이 재빌드되며 `UIDocument.panelSettings` 누락 문제가 씬 데이터와 빌더 쪽에서 보정됐다.
- `RunSessionConfig` static 상태가 제거되고 `RunSessionBootstrap`으로 선택 상태가 이동했다. 씬 전환 책임이 더 명확해진 점은 좋은 전진이다.
- heal soul material, damage digit texture, vertical slice audio setup이 추가되어 이전 리소스 미할당 위험이 상당 부분 해소됐다.
- 캐릭터 특수 프로필과 특수 이동 브리지가 들어오면서 수직 슬라이스의 플레이 표현 범위가 넓어졌다.
- EXP 주입, damage 적용, game-over save check가 smoke 경로에서 복구되어 회귀 대응 속도는 양호하다.

## 2. 코드 품질 리뷰
이번 변경의 핵심은 기능 코드보다 씬 구성과 브리지 연결이다. `RunSessionConfig` 삭제와 `RunSessionBootstrap` 도입은 static 세션 상태를 줄였다는 점에서 방향이 맞다. 왜 중요한가 하면, static 선택 상태는 씬 재로드와 테스트 순서에 따라 결과가 달라지는 전형적인 Unity 회귀 원인이다. 개선 방향은 지금처럼 씬 오브젝트가 상태 소유권을 갖고, gameplay 씬 소비 시점을 명확히 만드는 것이다.

반면 씬 YAML 변경량이 매우 크고, `RebuildAllScenes`, `MainMenuSceneBuilder`, `UISceneSetup`이 동시에 바뀌었다. 이 구조는 자동 생성 자체가 문제라기보다, 생성 결과를 검증하는 테스트가 없으면 `m_PanelSettings`, `sourceAsset`, bridge 참조 누락이 런타임에서만 터진다는 점이 위험하다. 빌더가 만든 씬에 대해 필수 화면 수, `UIDocument.panelSettings`, `UIGameFlow.runSessionBootstrap`, HUD bridge 참조를 검사하는 editor validation을 붙이는 편이 좋다.

자료구조/복잡도/할당 관점에서는 이번 diff 범위에서 명확한 O(n²) 탐색이나 hot path LINQ 할당 증거는 보이지 않는다. 다만 `sfxClips`처럼 Inspector 배열 크기와 enum/index 기반 호출이 맞물리는 필드는 방어 코드만으로 끝내지 말고, 빌더 단계에서 배열 길이와 필수 clip 할당을 검증해야 한다. 현재 비용은 런타임 무음 실패이고, 대안은 enum-indexed table 검증이다.

## 3. 진행도 평가
네트워킹 구현은 현재 수직 슬라이스 범위에 직접 포함되지 않으므로 구현 경로 평가는 해당 없음에 가깝다. 대신 DOTS 기반 단일 플레이 수직 슬라이스 기준으로 보면, 씬 흐름·UI Toolkit 화면·리소스 할당·smoke 복구가 이어져 제출 가능한 형태에 가까워졌다.

진행도는 68%로 본다. 반복 시연 가능한 뼈대는 있으나, 이번 커밋의 많은 부분이 씬 재생성과 fix 계열이라 검증 없이는 안정성을 확정하기 어렵다. 특히 모바일 화면에서 digit/effect 가독성, 분리 시스템 성능, Burst 제외 시스템 재검증은 아직 제출 전 리스크다.

## 4. 다음 권장사항
- Rebuild All Scenes 후 MainMenu → CharacterSelect → DotsVerticalSlice 흐름을 PlayMode smoke로 고정한다.
- 일시정지·도감·업적 화면까지 UI Toolkit 자동 조작 smoke를 확장해 UXML name 누락을 조기에 잡는다.
- damage digit atlas와 특수 이펙트 크기·알파를 모바일 실기 또는 동일 해상도 캡처로 확인한다.
- `EnemySeparationSystem` 최적화 결과를 문서의 모바일 목표 프레임 기준으로 다시 측정한다.
- Burst 제외 시스템은 Unity/Entities 업그레이드 후 컴파일 가능 여부와 성능을 재검증한다.

## 5. 문서화 상태
design은 8점이다. `docs/planning/game-design-spec.md`, `docs/planning/ui-plan.md`, 발표 요약 문서가 있어 게임 루프와 UI 흐름은 실무적으로 따라갈 수 있다. 다만 일부 unlock·밸런스 규칙은 코드와 문서에 나뉘어 있다.

technical은 8점이다. assembly boundary, folder/asmdef layout, live-data patch boundary, DOTS rebuild 전략 문서가 충분하다. 신규 참여자가 구조를 읽는 데 도움이 되지만, 최신 씬 빌더 검증 절차는 아직 문서보다 코드 변경에 더 의존한다.

spec은 7점이다. 씬 구성, UI 화면 목록, migration todo, baseline 문서가 있어 체크리스트로 쓸 수 있다. 다만 실제 수치 테이블과 smoke pass/fail 기준이 한곳에 완전히 모이지 않아 제출 전 QA 기준으로는 한 단계 더 정리가 필요하다.
