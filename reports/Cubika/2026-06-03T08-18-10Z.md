# Cubika — 첫 수직 슬라이스 스냅샷

## 1. 주요 변경사항
- Unity 프로젝트 기본 구조, `.gitignore`, 라이선스, README가 추가되어 저장소 형태는 갖춰졌다.
- 큐브 데이터, 프리팹, 스프라이트, 애니메이션, 사운드가 대량 추가되어 실제 플레이 가능한 퍼즐 게임 재료가 들어왔다.
- `Cube`, `Hand`, `GameManager`, `NextCubeCtrl`, `OverCheck` 등 핵심 게임 루프 스크립트가 작성됐다.
- 모바일 입력 대응으로 `PlayerInput.inputactions`, `VirtualDPad`, safe area, editor setup, Android build 관련 코드와 일부 EditMode 테스트가 추가됐다.

## 2. 코드 품질 리뷰
좋은 점은 명확하다. 단순 씬 실험에서 끝나지 않고 `CubeData` ScriptableObject, prefab, Input System, 모바일 설정 테스트까지 도입했다. 특히 학습 프로젝트에서 입력 시스템과 빌드 설정을 테스트로 묶은 선택은 칭찬할 만하다. 이 방향은 나중에 플랫폼별 회귀를 줄이는 데 실제 효과가 있다.

위험 신호도 분명하다. `MobileControlsBootstrap.cs`가 695라인, `MobileControlsSceneSetup.cs`가 331라인으로 추가됐고, `SampleScene.unity`도 1만 라인 이상 크게 변했다. 왜 문제냐면 UI 생성, 입력 연결, safe area, 게임오버 처리 같은 변경이 한 덩어리로 붙으면 한 기능 수정이 다른 기능을 깨뜨려도 리뷰에서 잘 보이지 않는다. 개선 방향은 런타임 부트스트랩, 입력 어댑터, UI 프리팹 배치, 에디터 자동 설정을 책임별로 분리하는 것이다.

자료구조/복잡도/할당 관점에서는 제공된 unified diff에 C# 본문이 거의 포함되지 않아 `List.Find`, LINQ, 매 프레임 할당 같은 확정 지적은 할 수 없다. 따라서 이번 diff 범위에서는 자료구조/복잡도 관련 명확한 지적 없음. 다만 큐브 낙하·합성 게임은 `Instantiate/Destroy`가 반복되기 쉬운 구조이므로 `Cube.cs`와 `NextCubeCtrl.cs`의 생성 경로는 Profiler로 검증해야 한다.

## 3. 진행도 평가
네트워킹 코드는 보이지 않으므로 구현 경로는 싱글 플레이 로컬 게임으로 판정한다. 멀티플레이/네트워킹 평가는 해당 없음이다. 선택한 경로 기준으로는 핵심 루프, UI, 사운드, 모바일 조작, 웹 배포 링크까지 있어 제출 가능한 수직 슬라이스에 가까운 상태다.

진행도는 68%로 본다. 반복 플레이 자체는 가능해 보이나, 구조 분리와 테스트 범위가 아직 얇다. 특히 모바일 입력과 게임오버는 시연 중 바로 드러나는 영역이므로 다음 단계에서 자동 테스트와 수동 QA 체크리스트로 고정해야 한다.

## 4. 다음 권장사항
- `Hand`의 입력·회전·bash 책임을 분리해 조작 버그의 원인을 좁혀라.
- 큐브 병합, 점수 증가, 게임오버 조건을 PlayMode 테스트로 고정해라.
- 모바일 컨트롤 생성은 코드 생성보다 프리팹과 설정 에셋 중심으로 낮춰라.
- 큐브 생성·합성 경로를 Profiler로 확인해 풀링 필요 여부를 수치로 판단해라.
- README에 실행 방법, 조작법, 빌드 절차, 현재 버전 기준을 추가해라.

## 5. 문서화 상태
design은 3점이다. README에 “수박게임을 모티브로 한 큐브 퍼즐”이라는 컨셉과 기본 목표는 있으나, 코어 루프의 의도나 플레이 경험 목표는 아직 설명되지 않았다.

technical은 1점이다. 현재 문서 스냅샷에는 아키텍처, 주요 클래스 관계, 입력 흐름, 빌드 절차가 없다. TextMesh Pro PDF는 외부 패키지 문서라 프로젝트 기술 문서로 보기 어렵다.

spec은 2점이다. 현재 버전과 플레이 링크는 있으나 입력, 큐브 등급, 합성 규칙, 점수, 게임오버 조건이 테스트 체크리스트로 쓸 수준은 아니다.

## 6. Backlog
- `SampleScene.unity` 중심 변경이 커서 프리팹 참조 깨짐과 씬 회귀가 리뷰에서 잘 보이지 않는다.
- 기술 문서가 없어 입력, 오디오, 게임 상태 흐름을 코드에서 직접 추론해야 한다.
- 큐브 등급과 밸런싱 수치가 사양서로 고정되지 않아 조정 기준이 흔들릴 수 있다.
