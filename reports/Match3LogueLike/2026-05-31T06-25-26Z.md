# Match3LogueLike — 런타임 피드백·QA 스냅샷

## 1. 주요 변경사항
- 전투 보상 SFX, 햅틱 토글, Act 기반 절차적 BGM, 첫 전투 튜토리얼이 추가되어 플레이 피드백 밀도가 크게 올라갔다.
- 맵·전투·보상·게임오버 UI에 안전영역 대응과 세로 화면 QA 기록이 들어갔다. 모바일 제출 관점에서 의미 있는 전진이다.
- 보상 오버레이 회귀 테스트가 추가되어 씬 소유권, 빈 선택지 처리, 로컬라이즈 라벨을 PlayMode에서 검증한다.
- `.claude` 에이전트·스킬·훅이 대량 추가되어 AI 협업 구조를 프로젝트 산출물로 남기기 시작했다.
- Gem 버스트 파티클이 Destroy 기반에서 ObjectPool 기반으로 바뀐 점은 명확히 좋은 개선이다.

## 2. 코드 품질 리뷰
가장 큰 경고는 `DamageNumberUI.cs`에 `CombatSfxFeedback`, `RunBgmController`, `FirstCombatGuideUI`까지 함께 들어간 구조다. 기능 자체는 전진했지만 파일 책임이 무너졌다. 왜 문제냐면 UI 데미지 숫자 수정, 오디오 수정, 튜토리얼 수정이 같은 파일 충돌과 리뷰 범위 확대를 만든다. 개선은 단순하다. 각 런타임 컨트롤러를 독립 파일로 분리하고, 공통으로 필요한 오디오 톤 생성 로직만 별도 helper로 빼는 편이 낫다.

Unity 관점에서는 `RuntimeInitializeOnLoadMethod`와 `DontDestroyOnLoad` 싱글톤을 여러 개 추가한 결정이 장기 위험이다. 지금은 편하지만 씬 전환, 테스트 격리, 옵션 초기화 순서에서 문제를 만들기 쉽다. 특히 오디오·튜토리얼·BGM은 전역이어야 하는 이유와 종료 조건이 문서화되어야 한다. 반대로 EventBus 구독/해제는 대체로 짝이 맞고, reward overlay 테스트에서 `EventBus.Clear()`를 호출한 점은 좋다.

자료구조/복잡도 측면에서는 `Gem` 파티클 풀링이 가장 긍정적이다. 기존 매치 연출마다 `new GameObject`와 `Destroy`가 반복되던 비용을 풀로 고정해, 캐스케이드가 많은 매치3 장르에서 프레임 스파이크를 줄일 수 있다. 남은 지적은 `ModifierRewardUI`의 unlockable 스킬 검사다. 현재는 해금 후보마다 보유 스킬을 다시 순회한다. 규모가 작을 때는 버티지만 콘텐츠가 늘면 `HashSet<SkillData>`를 한 번 만들고 membership lookup으로 바꾸는 편이 더 단순하고 안전하다.

## 3. 진행도 평가
네트워킹 코드는 없는 싱글플레이 수직 슬라이스로 판단한다. 보드-전투-런-보상-맵 흐름은 이미 낮은 수준의 반복 시연이 가능하고, 이번 범위에서 오디오·햅틱·튜토리얼·안전영역·회귀 테스트가 붙어 제출용 완성도에 가까워졌다.

다만 제출 가능한 빌드 기준으로는 아직 세로 화면 실기 검증, 런타임 싱글톤 수명 정리, UI 문자열 로컬라이즈 마감이 남아 있다. 진행도는 68%로 본다. 방향은 좋지만 지금부터는 기능 추가보다 QA 폐쇄와 구조 정리가 더 높은 가치를 가진다.

## 4. 다음 권장사항
- `DamageNumberUI.cs`에 합쳐진 SFX, BGM, 튜토리얼 클래스를 각각 독립 파일로 분리한다.
- `portrait-layout-qa.md`의 잔여 항목을 실제 맵→전투→보상→게임오버 플로우에서 닫는다.
- `MapScreenUI`의 `"VIB ON"`, `"VIB OFF"`를 localization key로 교체한다.
- `ModifierRewardUI`의 보유 스킬 중첩 순회를 `HashSet<SkillData>` 조회로 바꾼다.
- 전역 런타임 싱글톤의 생성·파괴·테스트 격리 정책을 아키텍처 문서에 추가한다.

## 5. 문서화 상태
design은 8점이다. `game-design.md`, `relics.md`, `modifiers.md`, `enemies.md`가 현재 코어 루프와 콘텐츠 방향을 충분히 설명한다. 단순 아이디어가 아니라 매치3와 로그라이크 결합 이유가 보인다.

technical은 7점이다. `architecture.md`, `asmdef-structure.md`, `script-structure.md`, `hooks-guide.md`가 신규 유입에 필요한 큰 그림을 제공한다. 다만 훅 문서가 사용자 절대경로와 글로벌 설정에 기대고, AI 협업 계획 일부는 실제 구현 상태와 어긋난다.

spec은 7점이다. `dev-plan.md`, `performance-qa.md`, `portrait-layout-qa.md`, `tutorial-reference.md`는 체크리스트로 쓸 수 있다. 아직 상점 가격, 실기 안전영역, 밸런스 수치 확정표는 미완성이다.

## 6. Backlog
- AI 협업 훅 설정이 사용자 절대경로와 글로벌 설정에 의존한다. 포트폴리오 산출물로는 좋지만, 재현 가능한 개발 인프라로 보려면 bootstrap 절차가 필요하다.
- 절차적 오디오는 외부 에셋 전 단계로 적절하지만, 볼륨 믹싱과 품질 조정이 코드 안에 갇혀 있다. 실제 음원 교체 지점을 분명히 남겨야 한다.
- 문서 로드맵과 실제 구현 상태가 일부 맞지 않는다. 특히 AI 협업 계획의 “다음 단계”와 현재 `.claude` 산출물 상태는 정리하지 않으면 신뢰도가 떨어진다.
