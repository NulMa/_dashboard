# Match3LogueLike — Phase 2 수직 슬라이스 스냅샷

## 1. 주요 변경사항
- Map → Battle → Reward → Map 흐름을 실제 씬 스모크로 검증했다. 세이브, 보상, 노드 방문까지 확인한 점은 제출 가능성 측면에서 의미가 크다.
- 보드 개입 이벤트, 특수 보석 조합, 적 서브액션, 계산형 스킬 modifier 테스트가 대폭 늘었다. 기능 추가보다 회귀 방지망을 먼저 넓힌 판단은 좋다.
- ModifierRewardUI가 외부 후보 주입을 받을 수 있게 바뀌고, GameFlowController가 카탈로그 기반 해금 후보를 발행한다. 데이터와 UI 사이의 결합이 전보다 낮아졌다.
- Map, Shop, Battle overlay, enemy portrait, gem readability 개선이 이어졌다. 다만 상당수 커밋이 fix 계열이라 UI 안정성은 아직 관찰 대상이다.

## 2. 코드 품질 리뷰
이번 범위의 가장 좋은 변화는 테스트의 방향이다. `RunLoopSceneSmokeTests`, `BoardInterventionSmokeTests`, `CombatBoardInterventionEventTests`는 단순 메서드 결과가 아니라 실제 이벤트 경계와 씬 전이를 검증한다. 특히 적 행동이 보드 이벤트로 이어지는 계약을 테스트로 고정한 것은 Board/Combat 분리 구조를 유지하는 데 도움이 된다.

반대로 런타임 UI 객체 생성 책임은 계속 커지고 있다. `Gem.cs`는 rim, shine, color glyph, tile glyph, special marker와 절차적 sprite 생성까지 한 클래스 안에 품고 있다. 왜 문제냐면 보석의 게임 상태 변경과 시각 자산 생성이 같은 변경면에 묶여, 작은 가독성 수정도 보드 런타임 리스크가 된다. 개선하려면 `GemView` 또는 `GemSpriteFactory`로 생성·캐시 책임을 빼고, `Gem`은 상태와 public API만 유지하는 편이 낫다.

자료구조/복잡도 측면에서는 `ModifierRewardUI`와 `SkillRewardSystem`의 후보 필터링이 아직 선형 membership 검사에 기대고 있다. 현재 스킬 수에서는 큰 병목은 아니지만, 보유 스킬·해금 스킬·후보 풀이 늘면 같은 `SkillData` 포함 여부를 여러 루프에서 반복한다. `HashSet<SkillData>`를 한 번 구성해 owned/unlocked/result 중복 판정을 고정하면 비용도 줄고, “이미 가진 스킬을 보상으로 보여주지 않는다”는 규칙이 더 읽기 쉬워진다.

## 3. 진행도 평가
네트워킹 코드는 확인되지 않아 구현 경로 분류는 해당 없음이다. 따라서 진행도는 싱글플레이 수직 슬라이스 기준으로 본다. 현재는 전투, 보드 개입, 보상 선택, 세이브, 맵 복귀까지 반복 시연 가능한 수준에 가까워졌다.

다만 상업적 완성도보다는 제출 가능한 수직 슬라이스 기준으로도 UI 런타임 생성 부채와 싱글톤 수명 정책이 남아 있다. 자동화 테스트는 강해졌지만, 실제 화면 가독성·씬 전환·정적 인스턴스 정리가 계속 fix 커밋으로 보정되는 흐름이라 risk는 medium이 타당하다.

## 4. 다음 권장사항
- `DamageNumberUI`는 오디오, 햅틱, 풀링 컨트롤러를 파일 단위로 분리해야 한다. 전투 UI 변경이 한 파일에 몰리면 다음 polish 단계에서 충돌이 커진다.
- `Gem.cs`의 절차적 sprite 생성은 전용 factory/view로 빼야 한다. 보석 규칙과 렌더링 생성 코드를 분리하는 것이 우선이다.
- ModifierReward 후보 필터링은 `HashSet<SkillData>` 기반으로 통합한다. 지금은 성능보다 규칙 중복과 누락 위험을 줄이는 목적이 더 크다.
- `RuntimeInitializeOnLoadMethod`로 살아나는 싱글톤은 씬 재로드 시 생성·정리 정책을 문서와 테스트에 명시해야 한다.

## 5. 문서화 상태
design은 8점이다. `documents/planning/game-design.md`, `modifiers.md`, `relics.md`, `enemies.md`가 현재 게임의 코어 루프와 보상 구조를 설명하고 있어 아이디어 나열 수준은 넘었다.

technical은 7점이다. `dev-structure.md`, `script-structure.md`, `smoke-tests.md`, `multi-agent-team-ops.md`가 실무적인 진입 문서 역할을 한다. 다만 `architecture.md`가 짧고 런타임 싱글톤·씬 수명 정책 같은 실제 위험 지점은 더 명확해야 한다.

spec은 8점이다. `portrait-layout-qa.md`, `performance-qa.md`, `todo.md`, handoff 문서들이 테스트 체크리스트와 현재 상태 추적에 유용하다. 최근 Phase 2 문서 갱신도 구현 상태와 비교적 잘 맞는다.
