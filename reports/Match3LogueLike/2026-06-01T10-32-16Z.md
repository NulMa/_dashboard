# Match3LogueLike — UI 안정화·검증 확장 스냅샷

## 1. 주요 변경사항
- 보드 입력이 모달 오버레이 뒤에서 막히도록 `GameplayInputBlockChangedEvent`와 회복 스모크 테스트가 추가됐다. 입력 버그를 재현 가능한 테스트로 잠근 점은 좋다.
- 보상, 상점, 게임오버, 맵 노드, 스킬 슬롯 등 UI 레이캐스트와 버튼 회복 테스트가 크게 늘었다. 최근 변경의 방향은 “고친 뒤 자동 검증”으로 바뀌고 있다.
- 다중 Codex 운영 문서, worktree 스크립트, handoff/evidence 흐름이 추가됐다. 협업 프로세스를 코드화한 점은 포트폴리오 가치가 있다.
- `Gem.cs`는 보드 가독성을 위해 마커·프레임·글리프를 강화했지만, 런타임 스프라이트 생성 책임까지 같은 클래스에 들어가 결합도가 높아졌다.
- localization guard와 placeholder 검증이 들어와 UI 문자열 회귀를 막는 기반이 강화됐다.

## 2. 코드 품질 리뷰
이번 변경의 가장 좋은 점은 결함을 “감”으로 고친 것이 아니라 PlayMode/EditMode 테스트로 고정했다는 점이다. 특히 보드 입력 회복, 오버레이 레이캐스트, 상점 종료 저장, 상태 패널 표시 같은 실제 플레이 중 끊기기 쉬운 경로를 테스트한 것은 실전적인 개선이다. 다만 테스트가 private field reflection 에 많이 의존한다. 이는 당장 유용하지만 내부 구현 이름이 바뀔 때 테스트가 행위가 아니라 구조에 묶인다. 다음 단계에서는 입력 잠금 상태나 보드 상태를 읽는 얇은 internal API 또는 test seam 을 두는 편이 낫다.

위험 신호도 분명하다. `DamageNumberUI.cs`는 이전 지적 이후에도 오디오·햅틱·풀링·런타임 초기화 책임이 같은 파일에 남아 있는 것으로 보인다. 이 구조는 작은 UI 수정에도 전역 런타임 부작용을 함께 건드리게 만들어 리뷰 누락을 부른다. `Gem.cs` 역시 보석 모델, 렌더 상태, procedural texture 생성이 한 클래스에 뭉쳤다. 기능은 동작하더라도 시각 폴리싱이 반복될수록 파일이 God Object 방향으로 커질 가능성이 높다.

자료구조/복잡도 관점에서는 `ModifierRewardUI`의 보유 스킬 판정이 아직 HashSet 기반으로 정리됐다는 근거가 부족하다. 보상 후보를 갱신할 때 보유 스킬 목록을 매번 선형 탐색하면 콘텐츠가 늘수록 UI 갱신 비용과 조건 분기가 같이 커진다. 이 프로젝트는 스킬·모디파이어 확장이 명시된 구조이므로, `SkillData` 또는 안정 id 기준 `HashSet`을 한 번 만들고 membership lookup 으로 고정하는 편이 더 단순하고 안전하다.

## 3. 진행도 평가
네트워킹 구현은 현재 범위에서 해당 없음이다. 따라서 진행도는 싱글플레이 framework 없는 Unity 수직 슬라이스 기준으로 본다. 전투 UI, 보드 입력, 맵/상점 흐름, 저장 복구, 보상 테스트가 연결되어 반복 시연 가능성은 70%대 초반까지 올라왔다.

다만 상업적 완성도가 아니라 제출 가능한 수직 슬라이스 기준으로도 아직 리스크는 medium 이다. 이유는 핵심 런타임 UI 컨트롤러 결합, placeholder 오디오, 문서 로드맵 불일치, 실제 기기 세로 QA 증거 부족이다. 방향은 좋지만 지금 1일 리팩터로 이후 2주 비용을 줄일 수 있는 부채가 보인다.

## 4. 다음 권장사항
- `DamageNumberUI.cs`에서 오디오, 햅틱, 데미지 숫자 풀링, 부트스트랩 책임을 분리한다.
- 세로 화면 QA는 문서 체크가 아니라 실제 전투→보상→맵→상점 전이와 기기 프로필 증거로 닫는다.
- `ModifierRewardUI`의 보유 스킬 판정을 `HashSet<SkillData>` 또는 안정 id set 으로 바꾼다.
- `RuntimeInitializeOnLoadMethod` 싱글톤의 생성 위치, 씬 전환 생존, 중복 방지 정책을 `architecture.md`에 명시한다.
- `Gem.cs`의 procedural sprite 생성과 렌더 상태 설정을 전용 뷰/팩토리로 뺀다.

## 5. 문서화 상태
design 은 8점이다. `documents/planning/game-design.md`, `modifiers.md`, `relics.md`, `enemies.md`가 현재 게임의 장르·콘텐츠·보상 구조를 꽤 구체적으로 잡고 있다. 다만 최신 UI/보드 폴리싱 결과가 GDD 본문과 완전히 연결됐는지는 더 봐야 한다.

technical 은 8점이다. `architecture.md`, `asmdef-structure.md`, `multi-agent-team-ops.md`, `smoke-tests.md`가 모듈 경계와 검증 흐름을 설명한다. 신규 작업자가 구조를 파악할 수 있는 수준이다. 단, 런타임 싱글톤 수명과 실제 구현된 에이전트 상태가 일부 문서에 늦게 반영된다.

spec 은 7점이다. QA, smoke, reward UI, tutorial reference 문서가 테스트 체크리스트로 쓸 수 있다. 그러나 밸런스 수치와 기기별 UI 판정 기준은 아직 자동 검증과 문서 증거 사이가 완전히 닫히지 않았다.

## 6. Backlog
- AI 협업 훅 설정은 repo 스크립트가 늘었지만 `hooks-guide.md`가 여전히 글로벌 settings 등록을 중심으로 설명한다. 다른 PC 재현성을 보장하려면 repo 상대 bootstrap 절차가 더 명확해야 한다.
- 문서 로드맵은 실제 구현된 `.agents/skills`와 PowerShell 운영 스크립트 상태를 따라가지 못한다. 포트폴리오 문서로 쓰려면 “계획”과 “현재 운용”을 분리해야 한다.
- 절차적 오디오는 override 경로가 생긴 점은 전진이지만, 기본 구현은 아직 placeholder 성격이 강하다. 볼륨, 품질, 에셋 교체 기준을 릴리스 품질 목표와 연결해야 한다.
